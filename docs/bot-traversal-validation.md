# 電腦走圖測試與地圖驗收程序

這份文件定義 `scripts/test-bot-traversal.ps1` 的用途、判定方式與地圖驗收門檻。此程序是地圖與
導航變更的必要回歸測試；**每一張日後新增的地圖，都必須加入同一套測試並通過單圖及全地圖驗證，
才可視為完成。**

## 測試範圍

PowerShell 外層腳本會逐張啟動遊戲的 `--traversaltest` 模式。每次執行使用固定步長模擬，並強制採用：

- 一位由神級電腦代打的本機主角
- 三名新手難度對手，降低交火對走圖結果的干擾
- 無擊殺、奪旗、支配得分與時間上限，確保測滿指定的有效遊戲畫格
- 視窗模式與低畫質，適合無人值守執行
- 每張地圖都以自己被設計的模式測試：0～12 死亡競賽、13～16 奪旗大戰、17～20 支配佔領、
  21～24 攻堅模式、25～27 突擊模式、28～33 戰爭模式、34～35 炸彈球。這十五張載具／目標
  地圖同時覆蓋節點、突擊目標、能量球、滑板、炸彈球與載具程式碼路徑；腳本預設範圍為全部 0～35
- `UNREAL99_BOT_DEBUG=1` 與 `UNREAL99_NAV_DEBUG=1` 的診斷輸出

測試不會鎖定、置中或移動桌面游標。一般執行期間仍可正常使用電腦。

## 執行方式

在儲存庫根目錄執行完整套件：

```powershell
.\scripts\test-bot-traversal.ps1 -Frames 3600
```

`3600` 是每張地圖 60 秒的有效遊戲時間，也是提交前的標準長度。腳本預設先建立 Release 版本，
再測試所有已登錄地圖。

只重測一張或數張地圖時，可指定編號：

```powershell
.\scripts\test-bot-traversal.ps1 -MapIds 7 -Frames 3600 `
    -OutputDirectory artifacts\bot-traversal-turbine -NoBuild

.\scripts\test-bot-traversal.ps1 -MapIds 7,11,12 -Frames 3600 `
    -OutputDirectory artifacts\bot-traversal-focused -NoBuild
```

`-NoBuild` 只能在目前 Release 輸出確定包含待驗證修改時使用。正式全套驗收不得使用過期的建置。
底層測試亦可直接呼叫：

```powershell
dotnet src\Unreal99\bin\Release\net10.0\Unreal99.dll `
    --traversaltest 3600 artifacts\single-map.png --map 7 --mode 0
```

### 投射物瞄準物理回歸

走圖測試驗證實際對戰整合；另以無視窗的 `--aimtest` 驗證提前瞄準的數學與投射物資料是否一致：

```powershell
dotnet src\Unreal99\bin\Release\net10.0\Unreal99.dll --aimtest
```

此測試逐案模擬投射物與目標抵達攔截時間的位置，涵蓋靜止目標、橫向移動、受重力的空中目標、
具有額外向上初速及下墜的彈道武器，以及速度超過投射物的不可達目標。可解案例的誤差必須不超過
`0.02 m`，不可達案例必須安全回退，不得產生無效方向；結束碼 `0` 與 `AIM_TEST PASS` 缺一不可。
修改電腦瞄準、武器投射物速度、重力、額外初速或壽命時，必須同時執行此測試與至少一張地圖的
3600 畫格實戰走圖測試。

## 自動判定門檻

遊戲每 0.2 秒採樣主角位置，並在結束時輸出一行 `TRAVERSAL_RESULT` JSON。下列條件全部成立才會
得到 `Passed: true`：

| 指標 | 通過條件 |
| --- | --- |
| 主角難度 | 神級的正規化值至少為 `0.999` |
| 對手難度 | 所有對手的正規化值不超過 `0.036`，即新手設定 |
| 總移動距離 | 至少 `max(80 m, 有效秒數 × 1.8 m)` |
| 探索範圍 | 至少 `min(10, max(6, floor(有效秒數 ÷ 7.5)))` 個 4 m × 4 m 格子 |
| 完全停滯 | 任一連續、沒有移動也沒有開火的停滯不得超過 8 秒；AS 合法站點與 BR 得分後 11 秒規則重置不計 |
| 原地來回 | 不得出現任何符合下列規則的抖動事件 |
| 視角卡地 | 向下超過約 60° 的視角不得連續維持超過 3 秒 |
| DOM 目標進度 | 三個控制點都至少真正被觸碰佔領一次，而且兩隊總得分大於零 |
| ONS 目標進度 | 至少完成一次節點建造，而且至少有一次實際載具登乘 |
| AS 目標進度 | 至少完成一個依序目標；地圖有載具即至少登乘一次，且第一回合任一角色的起始重生點 60 m 內若有該隊或中立載具，攻方／防守方各自都必須至少登乘一次 |
| WAR 模式動作 | 至少拾起一次能量球並至少使用一次氣墊滑板；節點建造與載具登乘仍須同時通過 ONS 門檻 |
| BR 模式動作 | 至少真正拾起一次中場球；輸出另記錄進球與傳球次數供人工複核 |

「原地來回」不是只看總距離。任一約六秒的移動視窗若同時符合下列條件，即記為一次失敗事件：

- 視窗涵蓋至少 5 秒，路徑長度至少 9 m
- 起點到終點的淨位移不超過 2.5 m
- 整段活動範圍不超過 6.5 m
- 至少三次大幅反向

目標路線另以較寬的活動範圍檢查兩點折返，避免電腦在長走廊內來回仍靠總里程通過。正式電腦邏輯
也會在 1.6 秒內兩度幾乎反向時先固定向有空間的一側繞障，並在 3.5 秒內沒有縮短旗幟、控制點、節點、
突擊目標或球門距離時暫時放棄該目標、先走向導航圖已證明可達的脫困點。

腳本亦會把遊戲非零結束碼或缺少 `TRAVERSAL_RESULT` 視為失敗，最後以結束碼 `2` 回報任何未通過
的地圖；全數通過時結束碼為 `0`。舊版 Intel WGL 驅動若在關閉視窗後重設，可能先輸出完整結果再
以 `0xC0000409` 結束，或讓下一個程序在遊戲碼執行前回報 `ApiUnavailable: WGL`。腳本只會針對
這兩種可辨識的基礎設施錯誤等待三秒並重試（最多三次）；一般遊戲測試失敗不會被重試掩蓋。

## 輸出與人工複核

預設輸出位於 `artifacts\bot-traversal\`：

| 檔案 | 用途 |
| --- | --- |
| `results.json` | 所有詳細結果，適合程式處理與保存完整診斷欄位 |
| `summary.csv` | 每張地圖一列的快速比較表 |
| `NN-map-name.log` | 該局的電腦狀態、導航及環境陣亡診斷 |
| `NN-map-name.png` | 測試結束畫面，用於確認位置與可見幾何 |

自動通過仍須人工複核，因為總距離不能證明每一條重要路線都正確。驗收人員應：

1. 確認 `results.json` 中每張地圖都是 `Passed: true`，而且程序結束碼為 `0`。
2. 檢查 `VoidDeaths`、`FallDeaths` 與 `LavaDeaths`。任一環境陣亡都會使自動驗收失敗，並且必須
   調查；不得接受電腦主動跳下邊緣、錯過跳台、離開升降台或反覆走進熔岩。
3. 檢查最長停滯、來回事件與最差視窗診斷；升降台的三維位移與實際開火會重設停滯計時，避免把
   破壞突擊目標時的有效定點射擊誤報為導航卡住；即使未越過門檻，明顯退化仍應修正。
   來回偵測採三維包圍範圍，因此跳台在不同樓層間的正常垂直路線不會被誤判為原地抖動；JSON
   會分別保留水平與垂直範圍供複核。
4. 閱讀單圖日誌，特別檢查 `WorstState`、路徑游標、目標節點、下一個節點與升降台狀態。
5. 打開結尾截圖，確認斜坡、三角牆、平台與護欄具有合理厚度，且主角沒有卡進幾何。
6. 對升降台、跳台、傳送門、窄橋、旗幟基地與地圖邊緣等特殊路線進行一次人工遊玩抽查。
7. CTF 地圖另須確認主角會向敵旗前進、拾取及攜帶旗幟、回到己方基地，並在己方旗幟歸位時得分。
8. DOM 地圖另須檢查 `ControlPointCaptures`、紅藍精確分數及日誌中的逐點歸屬；確認隊員分流進攻、
   缺彈時繞取補給，防守者在點外巡邏，而且同時站在點內的兩隊不會產生連續易主訊息。
9. ONS 地圖須檢查 `OnslaughtNodeCaptures`、兩隊持有節點數、`VehicleBoardings` 與
   `VehicleKindsDriven`；確認電腦只進攻連線可達的節點、能自動建造／脈衝支援、節點生成載具隨
   所有權啟用，且不會站在建造中的節點中央不動。
10. AS 地圖須檢查 `AssaultObjectiveCompletions`、`AssaultRoundsCompleted`、
    `AssaultAttackerVehicleBoardings`、`AssaultDefenderVehicleBoardings` 與回合／完成數欄位；確認目標
    嚴格依序、佔位只由圈內步兵攻方推進、完成後前推重生點、攻守交換與第二回合計時正確；也要確認
    兩個角色都會善用起始載具、駕駛不射擊非破壞目標，並在步兵互動目標前下車。
11. WAR 地圖須檢查 `WarfareOrbPickups`、`WarfareOrbCaptures`、`HoverboardRides`、節點持有數與載具
    遙測；確認電腦持球時不登車、會用滑板跑球、優先追殺敵方持球者，且支援／倒數／載具節點不會
    被一般連線規則錯誤鎖住。

### 全載具電腦操控回歸

`--vehicletest` 會在 ONS-托蘭把神級的正式 `BotController` 依序放入十七種載具，讓它追逐真實的
攻堅目標。每一種都必須成功登乘、行駛超過 3 m，並轉向超過 0.12 rad；每個武裝車種之後還要把
正式神級電腦對準一名可見敵人並證明它會開火，再由正式 `PlayerController` 對同一座位開火。測試
不是直接呼叫油門或射擊函式，因此同時覆蓋目標選擇、登乘距離、載具導航、卡牆復原、電腦感知／
瞄準、玩家輸入派送與四種運動解算：

```powershell
dotnet src\Unreal99\bin\Release\net10.0\Unreal99.dll --vehicletest
```

必須看到十七列 `VEHICLE_AI_CASE ... PASS`；武裝車種每列均須同時有 `botFire=True` 與
`playerFire=True`，最後總結 `VEHICLE_AI_TEST PASS`，且程序結束碼為 0。

另跑 `--vehiclecontrol`。它會以真實碰撞箱讓每一種地面／氣墊／步行載具駛上 0.55 m 平台再駛下，
並讓每一種飛行載具在失去駕駛後由 22 m 高處降落；同時確認關卡安置後的車體中心在執行期不會被
重複加上半高。托蘭還有兩層平台門檻：每輛停在高於步進高度的車旁必須有斜道或跳躍墊，並且正式玩家碰撞解算
必須能讓玩家不跳躍、持續向前走上 1.2 m 中央載具台。這是平台可進出、部分車上不了、以及飛行員死亡後載具懸空三類回歸的無視窗門檻。

環境陣亡既是遙測欄位，也是 `Passed` 布林值的自動條件；人工複核仍須判斷死亡原因與幾何品質，
不可只看腳本最後的 PASS 字樣就省略複核。

## 失敗調查與重測

先使用 `-MapIds` 重現單張地圖，再從 JSON 的 `WorstPosition` 和日誌中的導航狀態定位問題。
常見檢查方向如下：

- 距離或探索格不足：無法取得目標、導航區域斷裂、道具目標不可達，或特殊通道未連接
- 停滯：目標節點落在碰撞體內、門檻／斜坡阻擋、升降台等待狀態未解除
- 原地來回：相鄰節點反覆重算、戰鬥側移蓋過路徑轉向，或避崖判定與特殊路線互相衝突
- 環境陣亡：平台缺少安全邊界、著陸區太小、跳台軌跡不穩定，或導航節點太靠近邊緣
- CTF 缺乏進度：旗幟目標不可達、攻守狀態未切換，或基地回程路徑不連通
- DOM 缺乏進度：控制點未登錄主要模式、點位不在地面導航圖、全隊分配到同一點，或補給目標壓過佔點任務
- ONS 缺乏進度：連線圖與 HUD 不一致、建造中的節點被當成靜止目的地、車輛生成台綁錯節點，
  或電腦追逐停在空中的飛行載具
- AS 缺乏進度：目前目標無法由導航圖到達、破壞目標被當成佔位、前進重生點未解鎖，或回合交換後
  仍使用第一回合的出生側／載具所有權；防守方完全不登乘起始載具、駕駛不在步兵目標前下車亦屬失敗
- WAR 缺乏進度：能量球生成點未啟用、持球者錯誤登車或傳送、滑板路線中斷、主節點被錯誤保護，
  或支援節點被連線規則排除
- BR 缺乏進度：中場球或球門不在導航圖、持球者沒有跑／傳／投的決策、護送者落在持球者後方，或
  11 秒得分重置被誤判為一般停滯

修正後依序執行：

1. 同一張地圖的標準 3600 畫格重測。
2. 與修改共用導航機制或特殊幾何的相關地圖重測。
3. 不使用 `-NoBuild` 執行完整全地圖套件，確認沒有回歸。
4. 重新完成輸出與人工複核清單。

## 新地圖的強制驗收

新增地圖時，必須在同一個變更中完成下列項目：

1. 為地圖分配穩定的 `MapId`，並把名稱加入 `scripts/test-bot-traversal.ps1` 的 `$mapNames`。
2. 擴充腳本的預設 `MapIds` 與編號範圍驗證，確保不帶參數的完整套件會自動包含新地圖。
3. 更新地圖到模式的選擇邏輯。不得假設所有新編號都是 CTF；應使用地圖實際支援的主要驗收模式。
4. 先以 `-MapIds <新編號>` 通過 3600 畫格單圖測試與人工複核。
5. 再執行包含所有既有地圖的完整套件，且每張圖都必須通過。
6. 在變更說明中記錄執行命令、完整套件通過數量，以及 `results.json` 的輸出位置。

缺少新地圖的腳本登錄、單圖結果、完整回歸結果或人工複核時，地圖驗收即視為未完成。
